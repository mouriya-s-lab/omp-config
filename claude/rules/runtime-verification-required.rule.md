# 没有端到端 runtime 验证 = 没做

任何会被人、agent 或自动化在生产或开发环境消费的代码、配置、prompt、skill、脚本、CI、依赖、部署清单、Dockerfile、compose 或 k8s 改动，没有实际 runtime 验证一律未完成。类型检查、编译、build、lint、mock unit test、diff/LLM review、相似历史和“改动很小”都不能替代实际执行。

## 验证强度

选最强可行路径：

1. **真实路径：** 用moat browser在真实用户入口或者当前的测试版本触发按钮、API、CLI、webhook 或部署，观察 DB、文件、消息、UI、下游等最终结果；Web 服务必须使用此档。
2. **集成测试：** 在接近生产的环境覆盖本次改动，不得虚构其存在或用其充数。

Web 服务必须启动本地 dev server 或目标环境，并用 `agent-browser` skill 以真实用户身份完整执行登录、进入功能、操作、提交、看到最终结果与持久化；每个关键节点都要核对页面、接口及 DB/下游副作用。单页 smoke、首页探活、单接口或 curl 只能辅助，不能替代这条完整业务路径。

## 完成要求

- 声称“做完 / done / 可以合并或部署”前，报告跑了什么、在哪里跑、观察到什么，以及这些结果为何证明改动正确，并提供可复现核对的命令、输出、截图、日志、URL 或响应。
- 无法验证时明确说明代码已改但仍未完成 runtime 验证、具体环境限制，以及用户应在何处如何验证；不得把验证责任无说明地推给用户。
- 验证失败后修复并重跑完整相关验证，不得只验证刚修的点。
- 完成形态仍按 `github-issue-pr-routing` 走 issue→PR；runtime 证据进入 PR，分层由 `writing-pr` 定义，不得以本地验证绕过 PR，WEB项目涉及UI的改动点必须截图并贴在PR body，没有截图视为没做。
- 沙箱 dry-run 只有在沙箱就是真实运行环境时才算端到端验证。
