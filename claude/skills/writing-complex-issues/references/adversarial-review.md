# 对抗审查与方法迭代

什么时候读我：issue 树写完后审查时；操作员说「重新验证一次，可能还有遗漏点」时；要检验或改进本方法自身时。

## 审查轮：换面扫，直到干涸

固定问法：「这个设计逻辑是否自洽？运行时行为逻辑上是否没有漏洞？」但**每轮换一个扫描面**，不重复上一轮的面。面的候选（按系统形态取舍）：

- 设计自洽面：设计有没有违反自己声明的原则的地方（最高价值的发现通常在这——设计自己打自己）。
- 主体面：边界校验了「写什么」，校验了「谁在写」吗？过期/越权/匿名调用者。
- 调用面全集：上一轮只看了核心操作，其余 API/命令/handler 盘点过吗？
- 字段面：核心字段之外，还有哪些字段能影响行为却不设防？
- 组合一致性面：每个值局部合法、全图是否自洽（死边、死锁、不可达）？
- **共享根因面**：多个 children 的症状是否同一结构缺陷的投影？是则该缺陷应已上升为契约 / 全局守则且各 child 引用之——否则每个 child 各修各的症状，同根因在未盘点的位置继续存活。
- **验收自身的洞**：已开 issue 的验收表能不能被最省事路径钻过（具名常量 grep 杀不掉内联字面量、「含用例」没写断言什么）。

纪律：

- **怀疑先核实**：每个怀疑点在代码里查实再下结论；落空的怀疑登记为正例（「查到 X 已经参数化，符合契约」），它和坐实的漏洞同样有信息量。无代码可查（纯草稿、指称未解析）时核实对象退化为方向原文与草稿自身的交叉一致性；涉及代码实态的怀疑不凭印象裁决——转为 audit child 登记义务或 spike。
- 发现按三类落地：新漏洞 → 新 child；已有 issue 验收缺口 → 该 issue 的范围补充 comment；重验通过 → umbrella 登记 comment，含**有意不修的 known-open**（写明为什么不修，防后人用错误手段去堵）。
- **干涸判定**：连续一轮无新发现。操作员要求再验时永远换新面再扫一轮，而不是复读上一轮。

## 方法自身的迭代：生成性基准

改进本方法（或将来 skill 化后维护它）用生成性测试，不用自我感觉：

1. 选一个**不是从本方法蒸馏出来的**真实工件——操作员手笔的 RFC/issue 树。从方法自身的来源工件测只会得到循环确认。
2. 假想操作员只给了一句方向，逐节问：「方法的哪个区块/规则会引出这段内容？」
3. 三种结果：引得出（覆盖）；工件有而方法引不出（**方法缺口**，补区块或规则）；方法要求而工件没有（方法的增值，确认它确实该要求）。
4. 缺口补完后，对子结构（工件的 children、comment 层）重复同一测试——父层测试通过不代表子层形态被覆盖（audit-as-树根、稳定编号、收尾 child 这类组织形态只在子层可见）。
