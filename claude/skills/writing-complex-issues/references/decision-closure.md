# 决策收口

什么时候读我：树上存在「归 PR 定」「形态待定」「报错还是告警再说」「二选一并落地」类留白，要收口时；或写作中遇到任何分叉不确定该不该当场定时。把方案分叉原样写进「预期结果」发布（「方案 A 或 B，选哪个待定」）也是留白——它把本该在树上完成的裁决转嫁给实现者。

## 三分类详则

| 类 | 定义 | 处置与理由 |
|---|---|---|
| a：已知事实与约束 | 业务动机、架构不变量、代码锚点、必须保持/不许残留的性质、已裁决的目标级决策 | 写，且自包含——继承的契约条款逐字快照进来。指针的代价：headless 读者被迫做跨 issue 图遍历，每一跳都是偏离点 |
| b：本质自由的实现细节 | key 命名、命令拼写、内部结构、模块划分 | 默认不写。写出来就成虚假约束——headless agent 会把它当真理，更优的实现被预先封死。想写时先试着用判据升格为 a 类；升不了格就是预言 |
| c：不实验不知道的 | 第三方行为、跨组件可行性、性能 | 标记为未知 + 实验路径 + 结果分支。把猜测包装成 spec 的代价高于留白：留白的洞看得见，伪装成已知的洞要执行到才炸 |

a/b 判据：**这个分叉的不同选择会不会改变操作员观察到的结果**。会 → 目标级，裁决后写入（a）；不会 → 自由细节（b）。a/b 误判是最大偏离源——最常见的形态是把目标级决策（停机语义、错误分级政策）误标成「实现细节归 PR」。

## 收口流程

待决项不回传操作员——此禁令只覆盖「手头事实 + 全局求解可判定」的设计决策。**操作员独有事实**（业务动机、商业约束、组织偏好）是例外：既不可调查（不在代码里）也不可自行裁决（不是你的事实），缺了就回传操作员问，或显式写「方向未提供，按 X 假设推进」并登记为镜头修正入口。把它硬裁决是预言，把方向复读当它已经在手是空心化——两者都让业务层失去衡量尺。流程：

1. **扫全树收集**所有留白决策点，逐个过三分类。
2. **可判定性测试**：手头事实 + 全局求解能可靠判定的 → 当场裁决；需要实验、子 issue 验证、或运行数据的 → c 类，进 umbrella「未决设计问题」区块并 gate 依赖它的 children。两个方向的失败是对称的：把不可判定项臆断成契约，和把可判定项回传操作员，浪费的都是同一种东西——本该由你完成的判断。
3. **裁决前先核实事实**：每个决策依赖的代码现状先查（一个「某机制其实是死代码」的发现可以把决策从「变更行为」简化为「定义行为」）。
4. **全局求解**：全部待决项 + 全部约束（契约、既有裁决、历史教训、升级现实、运维路径）合进一个临时文件一起解——决策相互耦合（受控通道与直接 API 的区分、同一把错误分级尺），逐个独立拍会拍出矛盾。临时文件是过程存档，权威记录是 umbrella 的 master comment。
5. **回填**：umbrella 发 master record（决策表 + 交叉自洽检查），每个受影响 child 发决策 comment。
6. **范围性质化**：裁决时把机制枚举改写成性质（「一切 X 路径都经 Y」），再明确实际保证机制、覆盖边界与真实验证路径。遵循全局 functional/ADT 偏好；语言与项目模型支持时优先用领域类型、受限构造和编译器穷尽检查，否则按项目惯例使用边界解析、运行时校验或协议约束。不预钉品牌类型或特定 union，不声称性质措辞或 typecheck 能自动覆盖所有运行时旁路；验收仍须直接观察目标结果。
